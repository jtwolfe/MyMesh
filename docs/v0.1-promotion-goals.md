# v0.1 promotion goals — maintainability first

**Purpose:** MyMesh should not ship a `v0.1.0` (non-alpha) release until the project is **well-formed and maintainable**. Features can wait; operational shape cannot.

This document turns “how we version, watch CVEs, and ship updates” into **explicit promotion gates**. Alpha (`0.1.0-alpha.N`) may thrash. **`v0.1.0` means we can keep the project healthy without constant heroics.**

Related: [ROADMAP.md](ROADMAP.md), [SECURITY.md](SECURITY.md), [RELEASE-HANDOFF.md](RELEASE-HANDOFF.md), [USAGE.md](USAGE.md).

---

## First principles

A personal mesh agent is closer to a **daemon product** than a library:

| Concern | Why it matters for MyMesh |
|---------|---------------------------|
| **Identity of builds** | Users run network-facing binaries that can open shell, files, and TCP tunnels |
| **Dependency health** | Most future alerts will be crates, not glamorous app 0-days |
| **Interop over time** | Multiple machines upgrade at different times |
| **Calm operations** | The maintainer should not need to babysit every advisory or every laptop |

Promotion is about **making the boring path automatic** and **making real emergencies rare and scripted**.

---

## Gate A — Versioning is a contract

**Goal:** Versions communicate risk and interop, not marketing.

| Goal | Maintainability outcome |
|------|-------------------------|
| **SemVer after alpha** | `MAJOR` = hard break (protocol, on-disk trust/state, or intentional CLI rupture); `MINOR` = features with interop; `PATCH` = fixes including security |
| **Alpha freedom ends at v0.1.0** | `0.1.0-alpha.*` may break freely; `0.1.0+` changes are deliberate and documented |
| **Protocol / state awareness** | Agents can detect incompatible peers or state rather than failing opaquely |
| **Boring git model** | `main` is the integration line; **tags** are what people install; avoid long-lived fork forests until multi-version support is real |
| **Changelog discipline** | Every tag has human-readable notes (what changed, who must upgrade, known limits) |
| **No floating “latest” without a tag** | Install docs always pin a tag or release asset |

**v0.1 ready when:** a newcomer can read the latest tag + changelog and know whether two machines can still talk.

---

## Gate B — Repository and release hygiene

**Goal:** The GitHub repo is the single source of truth for what “released” means.

| Goal | Maintainability outcome |
|------|-------------------------|
| **Tag = release identity** | Every user-facing build maps to an immutable git tag |
| **GitHub Releases for binaries** | Optional assets (e.g. `mymesh-linux-x86_64`) live on the release, not random drive links |
| **Checksums with binaries** | SHA256 (signatures later) so upgrades are verifiable |
| **Release handoff is written** | [RELEASE-HANDOFF.md](RELEASE-HANDOFF.md) stays accurate for tag + upload |
| **Docs match the tag** | README / USAGE / security notes do not describe vapor for that tag |
| **CI is trustworthy before it is loud** | When CI is enabled: build + tests/audit on PR/tag; release workflow attaches artifacts |

**v0.1 ready when:** cutting a patch release is a checklist, not archaeology.

---

## Gate C — Supply chain and CVE posture

**Goal:** Dependency noise is automated; real risk is triaged by reachability and attacker model.

### C1 — Dependencies (majority of alerts)

| Goal | Maintainability outcome |
|------|-------------------------|
| **Committed lockfile for the binary** | Reproducible releases; upgrades are intentional |
| **Automated dependency PRs** | Dependabot or Renovate on Cargo |
| **Advisory gate in CI** | `cargo audit` (or equivalent) fails known-vulnerable graphs when CI is on |
| **Scheduled dep train** | e.g. monthly minor/patch for routine bumps; out-of-band for critical reachable issues |
| **Triage rubric** | Ask: reachable from `serve` / network path? linked-peer vs world vs local user? fixed version available? |

### C2 — First-party code (rarer, higher impact)

| Goal | Maintainability outcome |
|------|-------------------------|
| **SECURITY.md reporting path** | Private reports via GitHub Security Advisories (or documented alternative) |
| **Threat model stays current** | [SECURITY.md](SECURITY.md) updated when surfaces grow (SSH tunnels, SOCKS, carrier, dial proxy) |
| **Honest power of “trusted peer”** | Docs never imply a linked device is harmless |
| **Written severity → response** | Example policy below is adopted or replaced explicitly |

**Example response policy (adopt or rewrite before v0.1):**

| Class | Target response |
|-------|-----------------|
| Critical RCE / auth bypass / trust bypass | Emergency patch release as soon as practical; GHSA as appropriate |
| High (sandbox escape, unexpected TCP exposure) | Patch within days |
| Medium / low | Next scheduled train or next minor |

### C3 — System libraries

| Goal | Maintainability outcome |
|------|-------------------------|
| **Clear linking story** | Document whether release builds are largely static and who ships OpenSSL/glibc updates |
| **Re-release on critical graph fixes** | Prefer shipping a new MyMesh tag over hoping distro Rust packages save agents |

**v0.1 ready when:** a RUSTSEC email has an obvious owner (bot PR + audit CI + human triage rubric), not a panic.

## Gate D — Update and distribution path

**Goal:** Machines can stay current without the maintainer SSHing into every host — without reckless silent takeover.

| Goal | Maintainability outcome |
|------|-------------------------|
| **GitHub Releases as backbone** | Even if UX is manual, the canonical “latest stable” is a release |
| **Documented upgrade ritual** | Same steps every time: fetch tag/binary → install → restart user unit → verify dial proxy / ping |
| **Interop note per release** | Changelog states if **all nodes must upgrade together** for a fix/feature |
| **Prefer notify over silent replace (initially)** | A future `update check` may tell users; auto-replace of a shell-capable agent needs policy + preferably signing |
| **Optional packages later** | deb/rpm/AUR reduce support load; they do not replace tags/releases |
| **No custom update server early** | GitHub is enough until scale forces otherwise |

**Phased distribution maturity (not all required on day one of v0.1):**

1. **Minimum for v0.1:** tags + notes + checksummed binaries + install/upgrade docs  
2. **Soon after:** in-product or CLI “update available” (user-approved apply)  
3. **When support load hurts:** distro packages; users may opt into unattended upgrades there  
4. **Only with care:** signed artifacts + staged/auto agent update + rollback story  

**v0.1 ready when:** “just upgrade both ends to ≥ x.y.z” is a complete answer for most bugs.

---

## Gate E — Runtime and product maintainability

**Goal:** The running system is operable by someone who is not in the author’s head.

| Goal | Maintainability outcome |
|------|-------------------------|
| **Single endpoint ownership** | Documented and enforced: agent owns iroh bind; CLI uses dial proxy |
| **User-unit lifecycle** | install / enable / status / journal path is boring and documented |
| **Config and state locations stable** | Paths and env vars documented; migrations intentional after v0.1 |
| **Safe defaults** | Joins closed unless armed; firewall never silently opened; SOCKS/DNS loopback by default |
| **Debuggability** | Status, ping, logs, and USAGE diagnosis flowchart stay accurate |
| **TUI/CLI parity policy** | Known CLI-only escapes documented rather than accidental |

**v0.1 ready when:** a broken mesh is diagnosable from docs + `status` / `ping` / journals without reading source.

---

## Gate F — Quality bar before calling it v0.1.0

**Goal:** Alpha experimentation ends with a coherent product slice, not a larger alpha.

| Goal | Notes |
|------|--------|
| **Core paths validated on real multi-machine use** | Link, shell, cp, agent restart, SSH and/or SOCKS as claimed in README |
| **Honest README feature matrix** | No “planned” items listed as done |
| **Security and install policy readable** | SECURITY + INSTALL-POLICY match behavior |
| **Roadmap separates maintainability debt from feature wishlists** | This file vs [ROADMAP.md](ROADMAP.md) |
| **CI enabled or explicitly deferred with date/criteria** | “Disabled forever” is not a maintainability plan |

Feature completeness (desktop GUI, full system DNS, packages) is **not** automatically a v0.1 gate unless we claim those features. **Maintainability gates are.**

---

## Explicit non-goals for promotion

These are fine to delay; they should not block a maintainable v0.1 if the gates above hold:

- Full L3 VPN / TUN  
- Silent auto-update of the agent  
- Supporting many old majors at once  
- Perfect TUI on every compositor edge case  
- Mobile mesh node / store apps  

---

## Operating rhythm after v0.1 (steady state)

Set once, then mostly calendar-driven:

| Cadence | Action |
|---------|--------|
| **Continuous** | Dependabot/Renovate; security advisory inbox; issues labeled bug/security |
| **Monthly** | Dependency train; audit clean; patch tag if needed |
| **On critical reachable advisory** | Out-of-band patch tag |
| **Quarterly** | Threat-model skim; prune stale deps; verify release handoff still works |

---

## Promotion checklist (copy into the v0.1.0 PR / issue)

- [ ] SemVer + changelog rules agreed and reflected in docs  
- [ ] Tag/release process works end-to-end (binary + checksum optional but preferred)  
- [ ] SECURITY.md + private reporting path  
- [ ] Dependency automation + audit story (CI on or scheduled alternative)  
- [ ] Upgrade/interop wording in release notes template  
- [ ] Endpoint/agent/dial-proxy model documented and stable  
- [ ] README/USAGE honest for the tagged tree  
- [ ] Severity → response policy written (section C2)  
- [ ] At least one multi-machine validation pass recorded  
- [ ] Roadmap updated: alpha closed, v0.1.0 shipped criteria met  

---

## Summary

**v0.1.0 is a maintainability milestone**, not a feature freeze fantasy.

Before we treat MyMesh as something to “just use,” it should be:

1. **Well-formed** — clear versions, tags, docs, state/protocol expectations  
2. **Observable** — upgrades and failures are diagnosable  
3. **Watchable** — CVEs and deps alert through GitHub automation  
4. **Shipable** — patch releases are routine  
5. **Honest** — trusted peers and network surfaces match the threat model  

When those goals are met, promoting off alpha is justified. Until then, remain on `0.1.0-alpha.*` and invest in the gates above.
